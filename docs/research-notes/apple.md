## 1. Frameworks and APIs by feature

- **Platform baseline:** deployment target iOS 26.0, which already has the Medications API, Foundation Models, AlarmKit, `BGContinuedProcessingTask` and `RecognizeDocumentsRequest`. iOS 27 shipped on 14 Sep 2026, so every iOS 27 API below (PCC model, 8K context, App Schemas and Siri AI, FM image input, FM system tools) sits behind `if #available(iOS 27, *)` with a working iOS 26 path. Test: every feature runs on an iOS 26 device. [§1 Platform status, Findings, Inferences]
- **Dose logging, source of truth:** doses and boosters live in the app's own store; one-tap logging from Watch, widgets, Controls and Siri writes there. Apple Health is an optional read-only import, never a write target. Test: no code path calls `HKHealthStore.requestAuthorization(toShare:read:)` with medication or dose types. [§2 HealthKit Medications API, Takeaway, Inferences]
- **Medication page, Health import:** HealthKit `HKUserAnnotatedMedication` (`hasSchedule`, `isArchived`, `medication: HKMedicationConcept`, `nickname: String?`) and `HKMedicationConcept` (`identifier`, `displayText`, `generalForm`, `relatedCodings`), listed with `HKUserAnnotatedMedicationQueryDescriptor` (predicates on `isArchived` and `hasSchedule`). ## 2. Capabilities, entitlements, App Groups, keychain groups

- **HealthKit capability** on the iPhone target (and the Watch target if the Watch reads Health). The entitlement key is not stated in the source (the standard key is `com.apple.developer.healthkit`). A privacy policy is required. [§17 Capability matrix; §3 HealthKit in general, Findings]
- **HealthKit background delivery:** `com.apple.developer.healthkit.background-delivery` (iOS 15+, watchOS 8+) must be present before calling `enableBackgroundDelivery(for:frequency:withCompletion:)`. [§3 HealthKit in general, Findings]
- **Possible gated medication entitlement (unresolved):** one developer hit "Authorization to read the following types is disallowed: HKMedicationDoseEventTypeIdentifierMedicationDoseEvent, HKDataTypeUserAnnotatedMedicationConcept". No Apple source mentions a special entitlement; Apple docs point to using `requestAuthorization(toShare:read:)` as the cause. Test on a real device in the first build. [§2 HealthKit Medications API, Findings, Gaps]
- **Time Sensitive Notifications:** an entitlement is required for `.timeSensitive`; its doc page returned 404 so the key was not captured (commonly `com.apple.developer.usernotifications.time-sensitive`, verify). [§17 Capability matrix; §8 AlarmKit and notifications, Gaps]
- **Critical Alerts:** `com.apple.developer.usernotifications.critical-alerts` needs Apple's request form and approval, which is unlikely for ADHD stimulant reminders (unverified); no feature may depend on it. [§8 AlarmKit and notifications, Findings, Inferences]
- **Push Notifications:** required for Live Activity push updates and push-to-start, server silent pushes and CloudKit sync; the source describes these flows but does not name the `aps-environment` entitlement. [§7 WidgetKit and Live Activities, Findings; §10 Background execution, Findings; §13 Data, sync and security, Findings]
- **Background Modes, Remote notifications:** required for SwiftData and CloudKit sync (silent pushes). [§13 Data, sync and security, Findings; §10 Background execution, Findings]
- **Background Modes for BGTaskScheduler:** Background fetch (for `BGAppRefreshTask`) and Background processing (for `BGProcessingTask`) plus registered task identifiers are not described in the source. [Not in source]
- **Continued processing GPU:** `com.apple.developer.background-tasks.continued-processing.gpu` only if a `BGContinuedProcessingTask` uses the GPU. [§10 Background execution, Findings]
- **iCloud with CloudKit:** iCloud capability plus Remote notifications only if CloudKit sync is chosen; App Review 5.1.3(ii) risk applies (see section 12). [§13 Data, sync and security, Findings, Inferences]
- **PCC entitlement:** `PrivateCloudComputeLanguageModel` "Requires entitlement" (name and request form unknown). Free use requires fewer than 2 million first-time App Store downloads and, per Apple's WWDC26 guide, App Store Small Business Program enrolment (MacRumors mentions only the downloads criterion). [§6 Foundation Models, Findings, Gaps]
- **On-device Foundation Models:** no entitlement; needs an Apple Intelligence capable device with Apple Intelligence enabled. [§17 Capability matrix]
- **App Intents based features:** App Shortcuts, Siri, Spotlight, Controls, widgets and Focus filters list no permission or entitlement; Siri AI is gated by device and locale, not by entitlement. [§17 Capability matrix]
- **Live Activities:** enabled with the `NSSupportsLiveActivities` Info.plist key, not an entitlement; the user can disable them. [§17 Capability matrix]
- **AlarmKit:** `NSAlarmKitUsageDescription` plus user authorisation; no entitlement listed. [§17 Capability matrix; §8 AlarmKit and notifications, Findings]
- **EventKit:** usage-description keys only, no entitlement. [§17 Capability matrix; §4 EventKit, Findings]
- **Family Controls (optional blocking):** the `com.apple.developer.family-controls` distribution entitlement is requested through Apple's form before App Store submission, separately for the app AND each Screen Time extension (Device Activity Monitor, Device Activity Report, Shield Action, Shield Configuration). [§9 Screen Time API, Findings]
- **Journaling Suggestions (optional):** `com.apple.developer.journal.allow`. [§15 Accessibility, Findings]
- **Location (optional errands):** "Always" location authorisation is needed for `CLMonitor` background relaunch. [§17 Capability matrix; §11 Location and MapKit, Findings]
- **App Group (required):** one App Group shared by the app, the widget extension (widgets, Live Activity UI, Controls), intents that run in the extension process, and any Screen Time extensions; it holds the dose store and the current plan. Reason: a widget `AppIntent` runs in the widget-extension process while `LiveActivityIntent` and `openAppWhenRun` intents run in the app process. [§13 Data, sync and security, Inferences; §7 WidgetKit and Live Activities, Findings]
- **App Group file protection:** `completeUntilFirstUserAuthentication`; plain `complete` would block extensions and background tasks while the device is locked (inference, not re-verified). Test: log a dose from a Control on a locked device that has been unlocked once since boot. [§13 Data, sync and security, Inferences, Gaps]
- **Extension state storage:** Screen Time extensions keep state in App Group `UserDefaults`, not SwiftData, because the monitor extension has a 6 MB memory limit. [§9 Screen Time API, Findings, Inferences]
- **Keychain:** BYO-AI provider OAuth tokens are stored in the Keychain; if own end-to-end encrypted sync is chosen, its keys are stored in iCloud Keychain. [§6 Foundation Models, Findings; §13 Data, sync and security, Inferences]
- **Keychain access group:** sharing tokens between the app, its extensions and the Watch app is not covered; needed only if an extension-process intent must call a network service. [Not in source]
- **Sign in with Apple and In-App Purchase capabilities:** not covered (`com.apple.developer.applesignin`; In-App Purchase for StoreKit 2). [Not in source]
- **Watch target:** inherits the iPhone app's Calendar access level; HealthKit medication types exist on watchOS 26 but reliable Watch medication read authorisation is untested. [§12 watchOS, Findings; §2 HealthKit Medications API, Inferences]

## 4. Notifications, background work and their budgets

- **Interruption levels** (`UNNotificationInterruptionLevel`, iOS 15+ and watchOS 8+): `.passive`, `.active`, `.timeSensitive` ("breaks through system notification controls", needs the Time Sensitive entitlement) and `.critical` ("bypasses the mute switch", needs the Apple-approved Critical Alerts entitlement). [§8 AlarmKit and notifications, Findings; §17 Capability matrix]
- **Level mapping:** user-opted hard medication and booster alarms use AlarmKit; task nudges use `.timeSensitive`; low-priority items use `.passive`; a Focus filter downgrades nudges during a study or work Focus. Test: with the configured Focus filter active, non-critical nudges stay quiet. [§8 AlarmKit and notifications, Inferences; §17 Capability matrix]
- **64 pending local notifications:** the system keeps only the soonest-firing 64 (an automatically repeating notification counts as one) and discards the rest; stated on the legacy `UILocalNotification` page and not restated in the current UserNotifications article. Schedule a rolling 24 to 48 hour window and refill on every launch, on background refresh and on `EKEventStoreChanged`. Test: with 100 candidate reminders the pending count never exceeds 64 and the next 24 hours stay covered. [§8 AlarmKit and notifications, Findings, Inferences]
- **Notification content:** no drug names in bodies that can show on the Lock Screen or be announced by Siri; push must not be required for the app to function and must not carry sensitive personal information (4.5.4). [§8 AlarmKit and notifications, Findings, Inferences; §16 App Store Review rules, Findings]
- **Siri on announced notifications (iOS 27):** set `appEntityIdentifiers` on `UNMutableNotificationContent` so Siri can act on the notification (for example "log it"). [§5 App Intents and Siri, Findings]
- **Notification actions:** listed as an event-driven entry point and as a lower-friction locked-device logging path than widget buttons; category and action types (`UNNotificationCategory`, `UNNotificationAction`) are not named in the source. [§10 Background execution, Takeaway; §7 WidgetKit and Live Activities, Inferences]
- **Critical alerts:** sound plays "even when the app is locked, muted, or a person uses Do Not Disturb focus", but approval criteria are login-gated and approval for non-emergency stimulant reminders is unlikely. [§8 AlarmKit and notifications, Findings, Inferences, Gaps]
- **AlarmKit (iOS 26, iPadOS 26, Mac Catalyst 26):** alarms break "through the silent mode and the current focus" without the critical-alerts entitlement; `NSAlarmKitUsageDescription`; authorisation through `AlarmManager.shared`, auto-requested on the first alarm; `Alarm.Schedule.fixed(_:)` or `.relative` with timezone-aware weekly recurrence; `Alarm.CountdownDuration(preAlert:postAlert:)`; custom secondary-button intents (for example "Log dose"); alarms appear on a paired Apple Watch; no numeric alarm limit stated. [§8 AlarmKit and notifications, Findings, Gaps]
- **AlarmKit countdown rule:** "If your alarm supports countdown functionality, your app is required to implement it using a Live Activity." [§8 AlarmKit and notifications, Findings]
- **AlarmKit voice control (iOS 27):** set `appEntityIdentifier` on `AlarmConfiguration` so "snooze it" works through Siri. [§5 App Intents and Siri, Findings]
- **No periodic background runtime:** `BGAppRefreshTask` gets up to about 30 seconds when the system decides; `BGProcessingTask` is for deferrable heavy work; real-world refresh frequency is unknown. [§10 Background execution, Findings, Gaps]
- **Silent push budget:** `content-available: 1`, `apns-priority` 5, `apns-push-type: background`, up to 30 seconds of runtime; more than three background pushes per hour are rate-limited. [§10 Background execution, Findings]
- **`BGContinuedProcessingTask` (iOS 26):** only for work a person starts in the foreground (for example "Re-plan my week" or a schedule import); progress shows in a system Live Activity the person can cancel; `.fail` and `.queue` strategies; GPU use needs its entitlement; the system cancels it if the person closes the app in the app switcher. [§10 Background execution, Findings, Inferences]
- **Event-driven maintenance:** re-plan the day, refill notifications and reschedule shields on every foreground launch, inside App Intent `perform()` (for example after a dose log), in HealthKit observer callbacks, in `BGAppRefreshTask` when granted, and optionally from a server-scheduled silent push at most about three per hour. [§10 Background execution, Inferences]
- **HealthKit background delivery:** many types cap at `HKUpdateFrequency.hourly` on iOS (for example `stepCount`); on watchOS most types are hourly and the app gets four updates or refresh tasks per hour only with a complication on the active face; set observer queries up in `didFinishLaunching` and always call the completion handler, because three misses stop delivery; `HKCorrelationType` is unsupported; support for `HKMedicationDoseEvent` is unknown. [§3 HealthKit in general, Findings; §2 HealthKit Medications API, Gaps]
- **Locked device:** the HealthKit store is encrypted while locked, so background reads can fail while writes still succeed. [§3 HealthKit in general, Findings]
- **Foundation Models in the background:** `LanguageModelSession.GenerationError.rateLimited` happens only when the app is backgrounded and exceeds the system limit; generate the daily top-5 in the foreground or inside a user-started `BGContinuedProcessingTask`. [§6 Foundation Models, Findings, Inferences]
- **Live Activity push budget:** priority 10 pushes count toward an hourly budget (number unknown), priority 5 pushes do not; `NSSupportsLiveActivitiesFrequentUpdates` exists for frequent updates and users can turn it off. [§7 WidgetKit and Live Activities, Findings, Gaps]
- **CloudKit sync wakes:** SwiftData and CloudKit sync rely on the Remote notifications background mode. [§10 Background execution, Findings; §13 Data, sync and security, Findings]
- **Location relaunch (optional):** if an iOS app is not running when a `CLMonitor` condition is satisfied, the system tries to launch it (location authorisation required); recreate the monitor with the same identifier on relaunch; monitoring only starts after the first unlock following a reboot. [§11 Location and MapKit, Findings]

## 5. Widgets, Live Activities, Controls, Action button, App Intents, Siri, Focus filters

- **Widget reload budget:** a daily budget "typically includes from 40 to 70 refreshes", about every 15 to 60 minutes; timeline entries at least about 5 minutes apart; app-intent interactions, foreground app time and animations do not count; WidgetKit push notifications also exist. Test: a heavy logging day stays inside the budget. [§7 WidgetKit and Live Activities, Findings]
- **Widget countdowns:** show focus-window countdowns with dynamic date text (`Text(timerInterval:)` or progress), never minute-by-minute reloads; reload timelines only on state changes such as a logged dose or a changed plan. [§7 WidgetKit and Live Activities, Inferences]
- **Widget interactivity (iOS 17):** `Button(intent:)` and `Toggle` in system small through extra large and in `accessoryCircular` and `accessoryRectangular` on iPhone and iPad. [§7 WidgetKit and Live Activities, Findings; §17 Capability matrix]
- **Locked device:** widget and Live Activity buttons and toggles are inactive until the person authenticates and unlocks; the spec must define what a locked tap shows. [§7 WidgetKit and Live Activities, Findings]
- **Intent process:** a widget `AppIntent` runs in the widget-extension process; `LiveActivityIntent` and `openAppWhenRun` intents run in the app process; both must reach the App Group store. [§7 WidgetKit and Live Activities, Findings]
- **Mac round-trip:** interactions with iPhone widgets on a Mac round-trip to the iPhone. [§7 WidgetKit and Live Activities, Findings]
- **Smart Stack relevance on iOS:** `TimelineEntryRelevance` (score, duration) and donated `PredictableIntent`s. [§7 WidgetKit and Live Activities, Findings]
- **Smart Stack relevance on watchOS:** `relevance()` with `RelevantIntentManager`, or `RelevanceConfiguration` with `RelevanceEntriesProvider` (watchOS only); `RelevantContext` covers date, inferred location, fitness and sleep; `RelevantContext.sleep(_:)` needs `sleepAnalysis` permission; `RelevanceConfiguration` widgets cannot be pinned. [§7 WidgetKit and Live Activities, Findings; §3 HealthKit in general, Findings; §12 watchOS, Findings]
- **Live Activity lifetime:** active up to 8 hours, then the system ends it and it can remain on the Lock Screen up to 4 more hours (12 hours maximum). [§7 WidgetKit and Live Activities, Findings]
- **Live Activity size:** static plus dynamic data "can't exceed a combined size of 4 KB"; pass IDs and a short state, never task lists. Test: encode the largest realistic state and assert it is under 4,096 bytes. [§7 WidgetKit and Live Activities, Findings, Inferences]
- **Live Activity sandbox:** no network access and no location updates inside the activity. [§7 WidgetKit and Live Activities, Findings]
- **Live Activity layout:** content truncates above 160 pt height. [§7 WidgetKit and Live Activities, Findings]
- **Starting a Live Activity:** from the foreground; from an intent conforming to `LiveActivityIntent` (works from a Control, the Action button or Siri while the app is backgrounded); or by push-to-start through `pushToStartTokenUpdates` (not possible on iOS 17.1 and earlier). [§7 WidgetKit and Live Activities, Findings, Inferences]
- **Scheduled start:** `Activity.request(attributes:content:pushType:style:alertConfiguration:startDate:)` must include an `AlertConfiguration`; scheduled activities count toward the per-app concurrent limit, which Apple does not quantify. [§7 WidgetKit and Live Activities, Findings, Gaps]
- **Live Activity fields:** `staleDate` set to the predicted wear-off, `relevanceScore`, `.transient` style; push payload keys `dismissal-date` and `stale-date`. [§7 WidgetKit and Live Activities, Findings, Inferences]
- **Medication-window activity:** started by the dose-log intent; shows onset, peak and wear-off with `Text(timerInterval:)` or progress; an extended-release dose that runs past 8 hours chains a second activity near the 8-hour mark (scheduled start with alert, or server push-to-start). Test: a 10-hour XR window stays visible from dose to wear-off. [§7 WidgetKit and Live Activities, Inferences; §17 Capability matrix]
- **Mirroring:** Live Activities appear automatically in the Apple Watch Smart Stack and as alerts, in CarPlay (compact presentation) and in a paired Mac's menu bar; declare `.supplementalActivityFamilies([.small, .medium])`; buttons and toggles do nothing in CarPlay. [§7 WidgetKit and Live Activities, Findings; §12 watchOS, Findings; §14 Mac and iPad, Findings]
- **User control of Live Activities:** people can disable Live Activities and frequent updates; `NSSupportsLiveActivities` is required. [§7 WidgetKit and Live Activities, Findings; §17 Capability matrix]
- **`ControlWidget`** (iOS 18, watchOS 26, macOS 26) appears in Control Center, on the Lock Screen and on the Action button; UI is template-based only. [§5 App Intents and Siri, Findings; §17 Capability matrix]
- **One-press "Log dose" control:** its intent conforms to `LiveActivityIntent`, logs the dose and starts the medication-window Live Activity in one press; this is the fastest non-Watch logging path. Test: an Action button press with the app terminated logs the dose and shows the Live Activity. [§5 App Intents and Siri, Inferences; §7 WidgetKit and Live Activities, Inferences; §17 Capability matrix]
- **App Shortcuts:** `AppShortcutsProvider` (iOS 16, watchOS 9, macOS 13) shortcuts are available immediately on install; promote them with `SiriTipView` and `ShortcutsLink`. [§5 App Intents and Siri, Findings]
- **Core intents:** `LogDoseIntent(medication:, kind: .primary or .booster)` and `StartFocusBlockIntent` exposed as App Shortcuts with phrases such as "Log my booster in <AppName>"; they work on all devices, including Apple Watch and through AirPods. [§5 App Intents and Siri, Inferences]
- **iOS 26 intent features:** `SnippetIntent`, `requestChoice`, `supportedModes` (`.background`, `.foreground(.dynamic)`), `UndoableIntent`, `@DeferredProperty`, `@ComputedProperty`, `onAppIntentExecution`, `AppIntentsPackage`. [§5 App Intents and Siri, Findings]

[§5 App Intents and Siri, Findings, Inferences]

[§5 App Intents and Siri, Findings]

## 6. HealthKit and EventKit specifics

- **Medications are read-only:** Apple DTS: "Medication data is read-only in HealthKit"; WWDC25: "Only the Health App can persist dose events"; WWDC26 added no write support. The app cannot push its logs to Health. [§2 HealthKit Medications API, Findings, Inferences]
- **Correct authorisation call:** `requestPerObjectReadAuthorization(for:predicate:)`; using `requestAuthorization(toShare:read:)` for per-object types "fails with an `errorInvalidArgument` error". [§2 HealthKit Medications API, Findings]
- **Prompt behaviour:** "The system always asks for permission, regardless of whether they previously granted it", so call it only from an explicit "Link medications from Health" action, never on launch. [§2 HealthKit Medications API, Findings]
- **Grant scope:** the person selects individual medications; authorising a medication also grants its dose events; when a medication is added in Health, Health itself asks whether to share it with already-authorised apps. [§2 HealthKit Medications API, Findings]
- **Queries:** medications through `HKUserAnnotatedMedicationQueryDescriptor` (filter on `isArchived`, `hasSchedule`); dose events through `HKSampleQuery`, `HKAnchoredObjectQuery` and `HKObserverQuery`, filterable by medication, log status and date. [§2 HealthKit Medications API, Findings]
- **Dirty dose data:** dose events "may be logged for days in the past, deleted and re-persisted when editing, or may be saved for reminders that were never interacted with"; use `HKAnchoredObjectQuery`, process deletions, de-duplicate by HealthKit UUID and never double count against app-logged doses. [§2 HealthKit Medications API, Findings, Inferences]
- **Enum values unverified:** `HKMedicationDoseEvent.LogStatus` (taken, skipped, snoozed, not interacted per the WWDC summary) and `HKMedicationDoseEvent.ScheduleType` cases were not retrieved. [§2 HealthKit Medications API, Gaps]
- **Platforms:** medication types exist on iOS, iPadOS, macOS, Mac Catalyst, visionOS and watchOS 26.0+; HealthKit data is available on iPadOS 17+; on macOS `isHealthDataAvailable()` returns false. [§2 HealthKit Medications API, Findings; §3 HealthKit in general, Findings]
- **Invisible denial:** "an app isn't aware when the user denies permission to read data. From the app's point of view, no data of that type exists"; treat missing data as unknown, never zero. [§3 HealthKit in general, Findings; §17 Capability matrix]
- **Locked store:** "your app may not be able to read data from the store when it runs in the background. However, your app can still write to the store." [§3 HealthKit in general, Findings]
- **Sleep:** `HKCategoryValueSleepAnalysis` values `inBed`, `awake`, `asleepCore`, `asleepDeep`, `asleepREM`, `asleepUnspecified` (old `asleep` deprecated); stage samples overlap `inBed` but not each other; Apple Watch records awake samples only between two sleep samples; infer last night's sleep from these. [§3 HealthKit in general, Findings, Inferences]
- **No Sleep Schedule API:** bedtime and wake-up times are not readable through HealthKit; ask the person or use a Shortcuts automation that calls an App Intent. [§3 HealthKit in general, Findings, Inferences]
- **State of Mind:** `HKStateOfMind` (iOS 18, watchOS 11, macOS 15) is an `HKSample` with `kind`, `valence`, `valenceClassification`, `labels`, `associations` and a public initialiser, so check-ins can be written as well as read (with update permission). [§3 HealthKit in general, Findings]
- **Heart signals:** `heartRate`, `restingHeartRate` and HRV (`heartRateVariabilitySDNN`, identifiers not re-verified) are readable to track post-dose heart rate; Watch-to-iPhone sync latency affects freshness and is unmeasured. [§3 HealthKit in general, Inferences, Gaps]
- **Other readable types:** `timeInDaylight` (iOS 17), `mindfulSession`, cycle types such as `menstrualFlow`, iOS 27 `menopausalState` and `bleedingAfterMenopause`, `hypertensionEvent`, high and low heart rate and irregular-rhythm events. [§3 HealthKit in general, Findings]
- **Health data rules:** no advertising use, no sale, no disclosure to third parties without permission, a privacy policy, no false data written to HealthKit, no personal health information stored in iCloud (5.1.3), HealthKit data use under 5.1.2(vi). [§3 HealthKit in general, Findings; §16 App Store Review rules, Findings; §13 Data, sync and security, Findings]
- **EventKit access levels (iOS 17, macOS 14, watchOS 10):** write-only apps "can't read or delete any events from the user's calendars, including the ones it creates"; full access is required for social-plan detection and edit tracking. [§4 EventKit, Takeaway, Findings]
- **Write-only side effects:** `sources` returns a single virtual source and `defaultCalendarForNewEvents` a single virtual calendar. [§4 EventKit, Findings]
- **Upgrade prompt:** calling read APIs after write-only access prompts once; if declined, further calls never prompt again, so request full access up front with a clear explanation. [§4 EventKit, Findings]
- **Reminders access:** full access only, with `NSRemindersFullAccessUsageDescription`. [§4 EventKit, Findings]
- **Watch access:** the Watch app's access level matches the iPhone app. [§4 EventKit, Findings]
- **Change notification:** `EKEventStoreChanged` describes no individual changes; refetch every `EKEvent` and `EKReminder` held; call `refresh()` on an object being edited; posted on the main actor. [§4 EventKit, Findings]
- **Identifiers:** `eventIdentifier` most likely changes when the event's calendar changes; `calendarItemExternalIdentifier` is stable across devices but can be duplicated (ICS imports, shared calendars plus invitations, delegates, subscribed calendars), is identical for all occurrences of a recurring event (use the start date), and on Exchange differs between iOS and macOS and between devices for reminders. [§4 EventKit, Findings]
- **Identity strategy:** store an app UUID in the event `url` (for example `myapp://block/<uuid>`) or `notes`; keep a local map of UUID to (`calendarItemExternalIdentifier`, `calendarIdentifier`, occurrence start date); on change, refetch the planning horizon, diff, and re-match missing items by URL or UUID. Test: moving an app block to another calendar keeps its link. [§4 EventKit, Inferences]
- **Recurring edits:** `EKSpan` `.thisEvent` versus `.futureEvents` creates detached occurrences whose identifiers need occurrence-date handling. [§4 EventKit, Inferences]
- **Dedicated calendar:** app blocks go on an app-created calendar the person can hide, which also simplifies move detection. [§4 EventKit, Inferences]
- **Calendar privacy:** calendars are never end-to-end encrypted, even with Advanced Data Protection; no medication names in event titles, especially on shared or Exchange calendars. [§4 EventKit, Findings, Inferences; §13 Data, sync and security, Findings]
- **Third-party calendars:** Google and Exchange calendars appear only if the account is added in Settings, with sync lag and identifier differences. [§4 EventKit, Inferences]
- **Reminders limits:** no subtasks, nesting, flags, sections or tags through EventKit; iOS 27 Reminders changes are user-facing only; assume no new `EKReminder` properties. [§4 EventKit, Findings, Gaps]
- **External event creation (iOS 27):** Calendar natural-language entry, Siri creating events from emails and messages, and Visual Intelligence batch-importing events from a photographed schedule all write into EventKit, where full access lets the app read them. [§4 EventKit, Findings, Inferences]
- **Social-plan classification and attendee contact lookup:** not covered by the source (`EKParticipant` and Contacts are not discussed). [Not in source]

## 7. Foundation Models: availability states, limits, guardrails, fallbacks

- **Platforms:** `SystemLanguageModel` is on iOS, iPadOS, macOS and visionOS 26+; the docs list no watchOS (a WWDC26 session table claims watchOS 27, unconfirmed); the Watch shows text generated on the iPhone or calls PCC on watchOS 27. [§6 Foundation Models, Findings; §12 watchOS, Findings]
- **Availability check:** read `SystemLanguageModel.default.availability` before every generation entry point. Cases named in the source: `.unavailable(.deviceNotEligible)` and `.unavailable(.modelNotReady)` "and other cases"; the matrix adds that Apple Intelligence must be enabled (the `.unavailable(.appleIntelligenceNotEnabled)` case name is not in the source, verify). [§6 Foundation Models, Findings; §17 Capability matrix]
- **`.available`:** generate the top-5 with a `@Generable` result type; show a deterministic list while generating (inference). [§6 Foundation Models, Findings]
- **`.deviceNotEligible`:** the research requires a non-LLM path for devices without Apple Intelligence; for an Apple Intelligence only product show an unsupported-device explanation and still provide a deterministic top-5 so planning works (inference). [§6 Foundation Models, Inferences; §1 Platform status, Findings]
- **`.modelNotReady`:** the model is not yet ready (for example still downloading); show the deterministic top-5 and regenerate once availability changes (inference). [§6 Foundation Models, Findings]
- **Apple Intelligence turned off:** explain how to enable it and use the deterministic top-5 meanwhile (inference). [§17 Capability matrix]
- **Context window:** 4,096 tokens per session on iOS 26.x and 8,192 on iOS 27 for newer devices; instructions, prompts, tool schemas, `Generable` schemas and outputs all count; overflow throws `LanguageModelSession.GenerationError.exceededContextWindowSize`. Test: the largest realistic day (tasks, events, dose state) plus output fits in 4,096 tokens. [§6 Foundation Models, Findings]
- **Token budgeting:** measure with `contextSize` and `tokenCount(for:)` (both `@backDeployed`; TN3193 updated 31 Mar 2026 for the 26.4 APIs); split work across sessions instead of one long session. [§6 Foundation Models, Findings]
- **Tools:** at most 3 to 5 tools per session. [§6 Foundation Models, Findings]
- **Structured output:** `@Generable` types for results; the research's example is `@Generable struct Shift {date, start, end, role}` for roster parsing, with inputs chunked to fit 4K. [§6 Foundation Models, Findings, Inferences]
- **Background rate limit:** `GenerationError.rateLimited` "will only happen if your app is running in the background and exceeds the system defined rate limit"; generate in the foreground or inside a user-started `BGContinuedProcessingTask`. [§6 Foundation Models, Findings, Inferences]
- **Model drift:** the model version changes with the OS (26.0 to 26.3, 26.4, 27.0); re-run a prompt regression set on every OS release. [§6 Foundation Models, Findings]
- **Languages:** check `supportedLanguages` against the person's language before generating; regional availability (for example Australia) is unconfirmed. [§6 Foundation Models, Findings, Gaps; §1 Platform status, Gaps]
- **Use cases:** `SystemLanguageModel` exposes use cases such as `contentTagging`. [§6 Foundation Models, Findings]
- **Role of the LLM:** natural-language summaries and planning suggestions only (the daily top-5 wording); the focus-window estimate stays statistical. [§6 Foundation Models, Inferences]
- **iOS 27 additions:** rebuilt on-device model with better tool calling, image `Attachment` input, `OCRTool`, `BarcodeReaderTool`, a Spotlight search (RAG) tool, `DynamicProfile`, `response.usage`, the `LanguageModel` protocol, and an open-sourced core framework. [§6 Foundation Models, Findings]
- **PCC fallback (iOS 27):** `PrivateCloudComputeLanguageModel().contextSize` is 32,768; reasoning via `ContextOptions(reasoningLevel:)` with `.light` and `.deep` (one summary also lists `.moderate`); needs internet, an Apple Intelligence capable device and an entitlement; per-user, per-iCloud-account daily quota (higher with iCloud+) read through `quotaUsage.isLimitReached` and `limitIncreaseSuggestion`; no token cost to developers under the free-use criteria. [§6 Foundation Models, Findings]
- **Third-party models (BYO-AI, iOS 27):** Claude and Gemini Swift packages plug into `LanguageModelSession(model:)` "through the same Swift API"; they need OAuth, Keychain token storage and per-token billing; 5.1.2(i) requires clear disclosure and explicit permission before personal data is shared with third-party AI. [§6 Foundation Models, Findings; §1 Platform status, Findings; §16 App Store Review rules, Findings]
- **Escalation order:** on-device model first, PCC for hard jobs on iOS 27, third-party only with explicit opt-in. [§6 Foundation Models, Inferences; §17 Capability matrix]
- **Guardrails:** the source says nothing about guardrails, refusals or unsupported-locale errors; the build must still catch them (for example `GenerationError.guardrailViolation`, `.refusal`, `.unsupportedLanguageOrLocale`; names not in the source, verify) and fall back to the deterministic top-5. [Not in source]
- **Health framing of generated text:** never phrase output as dosing instructions (1.4.2); effect-window content carries "not medical advice, check with your doctor" copy (1.4.1). [§16 App Store Review rules, Findings, Inferences]
- **Unknowns:** on-device parameter count, and whether 8,192 tokens applies to all Apple Intelligence devices or only newer ones. [§6 Foundation Models, Gaps]

## 11. Accessibility and Liquid Glass rules

- **Assistive Access:** ship an `AssistiveAccess` SwiftUI scene (iOS 26+) with large Log Dose, Now and Next buttons; it doubles as a low-cognitive-load mode for ADHD users. Test: with Assistive Access on, the app opens the simplified scene. [§15 Accessibility, Findings, Inferences; §17 Capability matrix]
- **Reduce Motion:** read `accessibilityReduceMotion`; "UI should avoid large animations" when it is on, so reel-style paging transitions and morphs fall back to simple cross-fades (applying this to reel paging is an inference). [§15 Accessibility, Findings]
- **Dynamic Type:** every screen, widget and Live Activity honours Dynamic Type; the Lock Screen Live Activity still truncates above 160 pt, so test the largest sizes there. [§15 Accessibility, Takeaway; §17 Capability matrix; §7 WidgetKit and Live Activities, Findings]
- **Voice paths:** Vocal Shortcuts can probably trigger App Shortcuts (unverified), so every core action (log dose, start focus block) needs an App Shortcut; Background Sounds has no developer API. [§15 Accessibility, Takeaway, Gaps]
- **Controls:** Control Center and Action button controls are template-based, so custom styling is not possible there. [§17 Capability matrix]
- **Journaling Suggestions (optional):** `JournalingSuggestionsPicker` needs `com.apple.developer.journal.allow`; "your app can't access the details for a suggestion until after a person chooses to share them"; iOS 17.2+ and iPadOS 26+; Mac Catalyst ignores it. [§15 Accessibility, Findings]
- **Not covered:** VoiceOver labels, hit-target sizes, Reduce Transparency and Increase Contrast for custom views, haptic alternatives and accessible charts need another source. [Not in source]
- **Liquid Glass coverage:** the research contains nothing on Liquid Glass; the rules below come from the local liquid-glass skill and should be checked against Apple's HIG. [Not in source]
- **Glass layer rule:** glass is for the navigation and control layer floating above content (tab bars, toolbars, floating buttons), not content backgrounds; never more than two glass layers, because glass cannot sample other glass. [Not in source: liquid-glass skill]
- **Glass grouping:** wrap nearby glass elements in `GlassEffectContainer(spacing:)`; use `@Namespace` with `.glassEffectID(_:in:)` for morphing and `.glassEffectUnion(id:namespace:)` to merge distant pieces. [Not in source: liquid-glass skill]
- **Glass defaults:** `NavigationStack`, `TabView` and toolbars are already glass in iOS 26 and must not get glass applied again; `.buttonStyle(.glassProminent)` for the primary action, `.buttonStyle(.glass)` for secondary actions. [Not in source: liquid-glass skill]
- **Glass system adaptations:** system glass densifies under Reduce Transparency, adds borders under Increase Contrast, drops morphing and specular motion under Reduce Motion and follows the Tinted setting (iOS 26.1+); custom backgrounds behind glass get none of this and must be checked by hand. [Not in source: liquid-glass skill]
- **Glass opt-out:** `.glassEffect(reduceTransparency ? .identity : .regular)` with `@Environment(\.accessibilityReduceTransparency)`. [Not in source: liquid-glass skill]
- **Glass tint:** tint sparingly and never as the only signal; pair tint with an icon and a label. [Not in source: liquid-glass skill]

## 12. Edge cases, failure modes and mitigations

- **Hard limits to design against:** Live Activity 8 hours active and 12 hours visible, 4 KB, 160 pt; widget reloads 40 to 70 per day with entries about 5 minutes apart; 64 pending local notifications; background refresh about 30 seconds; silent pushes throttled above 3 per hour; HealthKit background delivery hourly on iOS and 4 per hour on watchOS with a complication; Foundation Models 4,096 tokens (8,192 on newer iOS 27 devices, 32,768 on PCC) and 3 to 5 tools; Screen Time monitor extension 6 MB; 20 `CLMonitor` conditions; one in-flight request per `MKDirections`. [§17 Capability matrix; §7 WidgetKit and Live Activities, Findings; §8 AlarmKit and notifications, Findings; §10 Background execution, Findings; §3 HealthKit in general, Findings; §6 Foundation Models, Findings; §9 Screen Time API, Findings; §11 Location and MapKit, Findings]
- **HealthKit read denied:** the app just sees no data. Mitigation: treat it as unknown, never zero, and show a "nothing shared from Health" state. [§3 HealthKit in general, Findings; §17 Capability matrix]
- **Health store locked:** background reads fail while locked. Mitigation: compute focus-window features on foreground or unlock and show optimistic UI on the Watch. [§3 HealthKit in general, Findings, Inferences; §12 watchOS, Inferences]
- **Background delivery silently stops:** three missed completion-handler calls end delivery. Mitigation: call the handler on every path, including errors, and register observers in `didFinishLaunching`. [§3 HealthKit in general, Findings]
- **Dirty imported doses:** back-dated, deleted and re-saved, or created for untouched reminders. Mitigation: anchored queries with deletion handling, de-duplication by HealthKit UUID, filtering by `logStatus`, no double counting with app logs. [§2 HealthKit Medications API, Findings, Inferences]
- **Wrong HealthKit call:** `requestAuthorization(toShare:read:)` with per-object types fails with `errorInvalidArgument` (and may explain the reported "disallowed" crash). Mitigation: only `requestPerObjectReadAuthorization(for:predicate:)`. [§2 HealthKit Medications API, Findings]
- **Repeated Health prompts:** the per-object sheet shows every time it is called. Mitigation: call it only from an explicit link action. [§2 HealthKit Medications API, Findings]
- **Calendar upgrade declined:** after a declined read prompt, further calls never prompt again. Mitigation: ask for full access once with a clear explanation; if refused, turn social-plan detection off and point to Settings (Settings path is an inference). [§4 EventKit, Findings]
- **Unstable event identity:** calendar moves change `eventIdentifier`; recurring occurrences share an external ID; Exchange IDs differ by platform; duplicates exist. Mitigation: own UUID in `url` or `notes`, local map with occurrence start dates, refetch-and-diff of the horizon on `EKEventStoreChanged`. [§4 EventKit, Findings, Inferences]
- **Calendar data exposure:** calendars are never end-to-end encrypted and can be shared. Mitigation: neutral titles with no medication names. [§4 EventKit, Findings, Inferences; §13 Data, sync and security, Findings]
- **Long XR window:** a Live Activity ends at 8 hours. Mitigation: chain a second activity near the 8-hour mark by scheduled start with `AlertConfiguration` or by push-to-start. [§7 WidgetKit and Live Activities, Findings, Inferences]
- **Oversized Live Activity state:** over 4 KB fails. Mitigation: IDs and short state only, with a size unit test. [§7 WidgetKit and Live Activities, Findings, Inferences]
- **Live Activities switched off:** the person can disable them or frequent updates. Mitigation: widgets, notifications and the app show the same window state (inference). [§7 WidgetKit and Live Activities, Findings; §17 Capability matrix]
- **Locked taps:** widget and Live Activity buttons do nothing until unlock. Mitigation: Watch logging, AlarmKit secondary buttons and notification actions as locked-device paths. [§7 WidgetKit and Live Activities, Findings, Inferences]
- **CarPlay:** Live Activity buttons and toggles do nothing there. Mitigation: treat the CarPlay presentation as read-only. [§7 WidgetKit and Live Activities, Findings]
- **Concurrency cap:** scheduled Live Activities count toward an unquantified per-app limit. Mitigation: at most one active plus one scheduled activity per dose window and handle request errors (inference). [§7 WidgetKit and Live Activities, Findings, Gaps]
- **Notification overflow:** beyond 64 pending, later reminders are dropped. Mitigation: rolling 24 to 48 hour window refilled on launch, refresh and calendar change. [§8 AlarmKit and notifications, Findings, Inferences]
- **Unreliable background time:** refresh timing is at system discretion and silent pushes above 3 per hour are throttled. Mitigation: event-driven maintenance with server push only as a backstop. [§10 Background execution, Findings, Inferences]
- **Continued task killed:** swiping the app away cancels a `BGContinuedProcessingTask`. Mitigation: resumable, idempotent re-plan and import jobs (inference). [§10 Background execution, Findings]
- **FM rate-limited:** background generation throws `rateLimited`. Mitigation: generate in the foreground and keep the day's result once generated (inference). [§6 Foundation Models, Findings, Inferences]
- **FM context overflow:** `exceededContextWindowSize`. Mitigation: pre-check with `tokenCount(for:)`, trim inputs, split into sessions, keep 3 to 5 tools. [§6 Foundation Models, Findings]
- **FM unavailable:** `.deviceNotEligible`, `.modelNotReady` or Apple Intelligence off. Mitigation: deterministic top-5 and regeneration when the model becomes available. [§6 Foundation Models, Findings, Inferences; §17 Capability matrix]
- **Model drift across OS versions:** outputs change between 26.0 to 26.3, 26.4 and 27.0. Mitigation: prompt regression tests per release. [§6 Foundation Models, Findings]
- **PCC quota reached or offline:** check `quotaUsage.isLimitReached`, fall back to on-device, surface `limitIncreaseSuggestion`. [§6 Foundation Models, Findings]
- **Siri AI missing:** older device, non-English locale, EU or China. Mitigation: plain App Shortcuts phrases keep voice logging working. [§1 Platform status, Findings, Inferences; §5 App Intents and Siri, Inferences]
- **Donations ignored:** excessive `IntentDonationManager` donations are dropped. Mitigation: donate only real interactions. [§5 App Intents and Siri, Findings]
- **Sensitive text on the Lock Screen:** notification bodies or Siri announcements could reveal medication. Mitigation: generic wording with no drug names; push payloads carry no sensitive data (4.5.4). [§8 AlarmKit and notifications, Inferences; §16 App Store Review rules, Findings]
- **AlarmKit overreach:** alarms override Silent mode and Focus. Mitigation: opt-in per alarm, easy to turn off, countdown alarms implemented with a Live Activity. [§8 AlarmKit and notifications, Findings, Inferences]
- **Watch offline or iPhone locked:** Watch logs cannot reach the iPhone immediately. Mitigation: local write, optimistic UI, `transferUserInfo` sync and de-duplication on arrival. [§12 watchOS, Inferences]
- **Watch background starvation:** without a complication on the face the Watch gets no guaranteed wakes. Mitigation: encourage adding the complication and never depend on Watch background refresh. [§12 watchOS, Findings]
- **Unpinnable relevance widgets:** `RelevanceConfiguration` widgets cannot be pinned. Mitigation: also ship a standard pinnable widget kind (inference). [§12 watchOS, Findings]
- **CloudKit schema lock-in:** production schemas are additive only, with no `.unique`, optional relationships only and no `.deny` delete rule. Mitigation: freeze the synced schema before launch and enforce uniqueness in code (inference). [§13 Data, sync and security, Findings]
- **Encrypted fields not queryable:** `CKRecord.encryptedValues` cannot be indexed or queried, can only be added as new fields and never live in the public database. Mitigation: query by non-sensitive keys and filter on device. [§13 Data, sync and security, Findings]
- **App Review 5.1.3(ii), health data in iCloud:** "may not store personal health information in iCloud". Mitigation: local-only with device-to-device sync, or own end-to-end encrypted sync with keys in iCloud Keychain, or CloudKit with `allowsCloudEncryption` plus explicit opt-in and privacy-policy disclosure; never mirror HealthKit-sourced data to iCloud. [§13 Data, sync and security, Findings, Inferences; §16 App Store Review rules, Findings]
- **App Review 1.4.2 and 1.4.1, dosing advice:** a booster prompt like "take X mg at 13:00" risks the dosage-calculator rule. Mitigation: phrase as "your logged booster usually happens around ...", use a clinician-set plan the person enters, and add "not medical advice, check with your doctor" copy to effect-window charts. [§16 App Store Review rules, Findings, Inferences]
- **App Review 5.1.2(i), third-party AI:** mitigation is a consent screen naming the provider and the data sent, shown before the first BYO-AI call. [§6 Foundation Models, Findings; §16 App Store Review rules, Findings]
- **App Review 5.1.1, accounts:** mitigation is in-app account deletion plus a privacy policy and consent. [§16 App Store Review rules, Findings]
- **Screen Time failures (optional):** `eventDidReachThreshold` fires with 0 minutes of usage on iOS 26.2 (FB21450954); 6 MB monitor memory; opaque tokens that expire; the person can revoke; about 35 percent of installs never pick an app; `DeviceActivityCenter.MonitoringError` (`excessiveActivities`, `intervalTooLong`, `intervalTooShort`, `invalidDateComponents`, `unauthorized`); "The system doesn't guarantee that the settings you specify govern the device's behavior". Mitigation: verify thresholds, stateless extensions, `TokenExpiryMessage` with `refresh(_:)`, register only the next few schedules and re-register on launch. [§9 Screen Time API, Findings, Inferences]
- **Location failures (optional):** 20-condition cap, no monitoring before first unlock after reboot, one `CLMonitor` per name. Mitigation: rotate the nearest or most urgent 20 errands and recreate monitors on launch, or use `EKReminder` location alarms. [§11 Location and MapKit, Findings, Inferences]
- **MapKit gaps (optional):** no opening-hours property and one request in flight per `MKDirections`. Mitigation: a new `MKDirections` per request; hours from the person or from Google Places shown on a Google Map with attribution and cached only as place IDs. [§11 Location and MapKit, Findings, Inferences]
