# PHASE 9 — CORE ENGINES, SEPARATE FROM THE UI (the most important design phase)

Outputs: `docs/ENGINE_SPEC.md`, `docs/PERSONALISATION_DESIGN.md`. Claude Code must never invent scheduling, medication or learning behaviour while building screens. Every engine is a pure, deterministic function in `PlannerDomain`: identical inputs (including the injected `now` and calendar) give byte-identical outputs; no randomness, no hidden clock, no network, no ML model files. Each engine row (`ENG-nnnn`) states inputs, outputs, constraints, invariants, algorithm, precedence, conflict resolution, fallbacks, confidence, explainability, persistence, safety boundaries, and a Source (`FEAT-`/`INT-`). Invariant aliases `INV-RL1`, `INV-RL2`, `INV-RL6`, `INV-RL7`, `INV-RL8` are required and each has a `TEST-`.

**EN-1 — FocusWindowEstimator** (internal name may be `MedicationWindowEngine`; UI name is always "focus window"). Inputs: dose log (UTC instant, Lifestyle id, medication-profile id — internal); check-ins (instant, answer ∈ {yes, partly, no}, source ∈ {watch, lockScreen, app, siri}); the user's stated estimate (start and end offsets in minutes after logging; optional latest-dose cut-off — internal, never used to suggest timing); active Lifestyle; `now`, calendar; optional covariates recorded for display only (previous night's sleep, workout that day). Method (fixed): for each check-in, offset = minutes since the most recent logged dose that local day (check-ins with no dose in the preceding 16 h are excluded); score 1 / 0.5 / 0; 30-minute bins over 0–16 h; each bin holds a decay-weighted mean (exponential, half-life 21 days) plus a prior from the stated estimate as pseudo-observations (n₀ = 6 per bin: 1.0 inside the stated window, 0.0 outside, 0.5 in boundary bins); the window is the longest contiguous run of bins with posterior mean ≥ 0.5, edges reported to the nearest 5 minutes; the ± interval is the minutes from each edge until a Beta(α = n₀·prior + Σw·score, β = n₀·(1−prior) + Σw·(1−score)) 80% credible interval would cross 0.5, capped at 180. Parameters live in one file with pinning tests. Output `FocusWindowEstimate { startOffsetMin, endOffsetMin, plusMinusMin, checkInCount, distinctDays, evidenceLevel ∈ {starting, early, usual}, basis, lifestyleId, computedAt, inputsHash }` mapping exactly to the brief's display states (`starting` < 3 distinct days shows the stated estimate; `early` 3–7 days; `usual` ≥ 8 days and ± ≤ 30 min). Disagreement flagged when `distinctDays ≥ 8` and |learned − stated duration| > max(60 min, plusMinusMin); the user's resolution (`accept`, `keepMine`, `askLater(until:)`) is an input; `keepMine` pins the stated estimate for planning; `askLater` suppresses for 7 days. All state is per Lifestyle; a new Lifestyle starts from the stated estimate or copies the current one on the user's choice. Every estimate is an immutable snapshot with `inputsHash`; the planner references a snapshot id; "Use my estimate" and "Reset learning for this Lifestyle" produce new snapshots, nothing is deleted. Invariants (tested): no output field describes a dose time, quantity or medication name; never reads medication class; idempotent; adding one check-in never moves an edge by more than one bin; zero check-ins → exactly the stated estimate; the check-in schedule (EN-4) tapers as `plusMinusMin` shrinks and never exceeds the budget.

**EN-2 — Scheduler.** Constraint-based greedy placement in priority order followed by bounded local search (≤ 200 deterministic swap/shift moves accepted only when a scored penalty falls). No LLM, no solver dependency. Horizon today + 6 days, ≤ ~100 items. Inputs: fixed events (calendar events, user-locked blocks); movable tasks (duration, deadline, priority, energy class ∈ {deep, body, social, admin}, first step, preferred window, dependencies, travel time); the current `FocusWindowEstimate` snapshot **anchored to today's actual logged dose** — with no dose logged today the planner uses the Lifestyle's baseline day and never a predicted dose time; day mode (ideal/baseline); brain-weather (low collapses the day to baseline); Lifestyle rules (wake anchor, quiet hours, paused routines); breaks and meals; `now`; calendar with explicit time zone. Precedence (explicit, in order): 1 locked events; 2 external calendar events; 3 deadlines inside the horizon; 4 deep work inside the focus window; 5 body/social/admin outside it; 6 user preferred windows; 7 dependencies; 8 minimise moves versus the previous plan; 9 fill remaining time. The engine never silently moves a locked item. Output `Plan { placements: [Placement { taskId, start, end, reason: PlacementReason, movedFromPreviousPlan }], unplaced: [Unplaced { taskId, reason }], overfullDay, snapshotIds }`; every placement carries a machine-readable reason so the UI can show "in your focus window (usual: 0:55–6:30 after logging)". Invariants (tested): locked items never move; no overlaps; quiet hours respected; deep work inside the window unless the user overrode it (flagged); identical inputs → identical plan; a placement never changes because of a dose event alone — only because the window snapshot changed; no code path creates, edits or suggests a dose; an overfull day yields `unplaced` entries with reasons rather than shrunk durations; the reason enum has no "missed" or "overdue" case.

**EN-3 — NotificationPlanner.** Plan + dose log + check-in schedule + budget → ≤ 48 h of local notification requests (never more than 60 pending, under the 64 cap), interruption levels, Discreet rendering, and the diff to apply. Reminder times are user data, never engine output (INV-RL6).

**EN-4 — CheckInScheduler.** 3–5 daily check-in instants while `evidenceLevel != usual`, spaced across the current estimate ± interval, avoiding quiet hours and locked events, tapering to ≤ 1 a day once `usual`.

**EN-5 — DiscreetFormatter / CopyLint.** The only function that renders medication-related strings; tests assert every string it can emit in Discreet mode contains no medication name, and that no string in the string catalog, App Shortcut phrases, notification templates or glanceable views matches the "Don't say" table or banned terms.

**EN-6 — LifestyleSwitcher.** Computes the preview as a diff between two Lifestyle rule sets ("Wake anchor 9:30 instead of 7:15 · study blocks move to afternoons · 6 term-only routines paused"), applies it transactionally, and produces the inverse diff for one-tap undo. Routines are paused, never deleted; external calendar events untouched.

**EN-7 — SupportSignpost.** The persistently-low rule: user's own brain-weather rating only (no derived score); fixed, documented, shown ("low on 5 of the last 7 days"); user-adjustable threshold and off switch; fires at most once per 7 days; never names a condition; never on the Lock Screen or in a notification (INV-RL7).

**Date and time rules for all engines.** `Calendar(identifier: .gregorian)` with `timeZone = TimeZone(identifier: <stored identifier>)!` injected; never `Calendar.current`, `TimeZone.current` or `Date()`; "tomorrow"/"next 7 am"/"same time next week" via `calendar.date(byAdding:)`/`nextDate(after:matching:)`, never +86 400 s; offsets since a dose are elapsed instants; wall-clock only for quiet hours, wake anchors and display. DST fixtures (NSW): DST ends Sunday 5 April 2026 (3:00 am AEDT → 2:00 am AEST, a 25-hour day) and Sunday 4 April 2027; DST starts Sunday 4 October 2026 (2:00 am AEST → 3:00 am AEDT, a 23-hour day) — verify against the NSW Government table this session and cite it.

**`docs/PERSONALISATION_DESIGN.md`.** MVP uses **no** machine-learning model, Core ML, Foundation Models or LLM for any product behaviour; the learner is EN-1. The document specifies: observations, inferred preferences, confidence, decay, Lifestyle scoping, manual correction, pattern changes, cold start, rollback, transparency ("every learned number shows what it is based on; standing changes need the user's approval" — design principle 8). Any later AI use case (e.g. screenshots/messages → tasks, v1+) is specified with: why AI is needed, inputs, outputs, fallback, privacy implications (8.1.3 stripping; on-device preferred), cost, latency, hallucination risk, validation, user confirmation, and Apple 5.1.2(i) consent if anything leaves the device. The app must never develop behaviour the user cannot understand or override.
